# M5 — Hybrid-search re-ranking — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use
> `superpowers:subagent-driven-development` (recommended) or
> `superpowers:executing-plans` to implement this plan task-by-task. Steps
> use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add a small, gated, post-RRF re-rank step on top of
M4's chunk-level recall so that long-PDF chunk hits are no longer
over- or under-counted relative to item-level hits. Re-rank is
**off by default** and **identity when off** — the default M5 build
behaves bit-identical to the post-M4 build.

**Architecture:** A single new function `rerankHits()` in
`packages/database/src/search-service.ts` is invoked from
`runSearch()` after `reciprocalRankFusion()`. The function takes the
fused hits + a small `RerankOptions` object and returns a re-ordered
list. The caller (`runSearch`) decides whether to call it, based on
`SEARCH_RERANK_ENABLED` (env var). When the env var is false or
`rerankHits` returns the input unchanged, the response shape is
unchanged. Query expansion is *not* in this plan; it is dropped
from the M5 scope per the spec.

**Tech Stack:** TypeScript 5.4, Node 22, no new dependencies.

**Spec:** [`./2026-10-08-p0-quality-upgrade-m5-m8.md`](./2026-10-08-p0-quality-upgrade-m5-m8.md) §2.1
(scope) and §36–§49 (M5 spec sections). The plan argues from the
spec; both travel together.

## Global Constraints

* Re-rank is **off by default** (`SEARCH_RERANK_ENABLED=false`).
  When off, every existing test must keep passing byte-for-byte.
* The re-rank `alpha` is a single module constant. Not a config
  knob, not a per-call option, not an env var.
* No new dependencies. No new SQL. No new migration.
* All Vietnamese error / log strings stay English; do not add any
  new copy in any other language.
* `pnpm typecheck` and `pnpm test` are both green at the end of
  every task.

## Review Focus

1. **Re-rank is identity when off.** A test must run `runSearch`
   with `SEARCH_RERANK_ENABLED=false` and assert the response is
   byte-equal to the pre-M5 response for the same input. The
   pre-M5 behaviour is the existing M4 behaviour, so the test
   can be expressed as "the post-M5 disabled state matches a
   snapshot of the post-M4 enabled state".
2. **Re-rank moves hits, not deletes them.** A re-ordered hit list
   must contain the same set of ids as the input. The cardinality
   of the response is preserved.
3. **The dashboard sees no change with the default config.** The
   web dashboard's `SearchResponse` consumer (see
   `apps/web/src/lib/api-client.ts`) must not be modified in M5
   unless the response shape changes. M5 is meant to be invisible
   to the UI; M7 is the milestone that surfaces it.

Each is wired to a task's test list.

export interface RerankHit {
  id: string;
  /** Original score (kept for explainability in M7). */
  score: number;
  /** Optional pre-computed embedding for the hit. null when the
   *  search did not compute one (lexical-only hits). */

  /** Per-leg scores for the explainability surface (M7). */
  lexical: number;
  vector: number;
  /** The post-RRF score before re-rank. */
  rrf: number;
}

export interface RerankOptions {

  queryEmbedding: number[] | null;
}

- [ ] **Step 2:** Add `rerankHits` at the bottom of
  `search-service.ts`, just before the `normalizeTagList` /
  `normalizeKindList` helpers:

```ts
/**
 * Re-rank a fused hit list by blending RRF with a second-pass
 * cosine similarity against the query embedding.
 *
 *   score = (1 - RERANK_ALPHA) * rrf + RERANK_ALPHA * cosine(query, hit.embedding)
 *
 * Identity when the query embedding is null (lexical-only path)
 * or when no hit carries an embedding. Cardinality is preserved.
 */
export function rerankHits(hits: RerankHit[], opts: RerankOptions): RerankHit[] {
  if (opts.queryEmbedding === null) return hits;
  const q = opts.queryEmbedding;
  const qNorm = l2norm(q);
  if (qNorm === 0) return hits;

  const scored = hits.map((h) => {
    if (!h.embedding) {
      return { hit: h, cosine: 0 };
    }
    const hNorm = l2norm(h.embedding);
    if (hNorm === 0) return { hit: h, cosine: 0 };
    return { hit: h, cosine: dot(q, h.embedding) / (qNorm * hNorm) };
  });

  return scored
    .map(({ hit, cosine }) => ({
      ...hit,
      score: (1 - RERANK_ALPHA) * hit.rrf + RERANK_ALPHA * cosine
    }))
    .sort((a, b) => b.score - a.score);
}

function dot(a: number[], b: number[]): number {
  let s = 0;
  for (let i = 0; i < a.length; i++) s += a[i] * b[i];
  return s;
}

function l2norm(a: number[]): number {
  let s = 0;
  for (let i = 0; i < a.length; i++) s += a[i] * a[i];
  return Math.sqrt(s);
}
```

```md
# M5 — Re-rank

## Why

A 200-page PDF that was searched for a phrase on page 80 used
to return nothing. M4 fixed that by indexing chunks. M5
improves the ranking of the chunks that come back.

## What

After the existing RRF blend, each hit's `rrf` score is
blended with a second-pass cosine similarity against the
query embedding:

    score = (1 - RERANK_ALPHA) * rrf + RERANK_ALPHA * cosine(query, hit.embedding)

`RERANK_ALPHA` is a single constant in
`packages/database/src/search-service.ts`. Today it is `0.3`.
It is not a config knob.

## Gate

The step is **off by default**. Set
`SEARCH_RERANK_ENABLED=true` in the API's environment to
turn it on. When off, `runSearch` returns the same hit
order as the post-M4 build, byte for byte. Cardinality is
preserved when on; only the order changes.

## Tests

- `packages/database/src/__tests__/search-rerank.test.ts`
  — pure unit tests for `rerankHits`.
- `apps/api/src/routes/__tests__/search-rerank.test.ts`
  — HTTP-level test for the env-var gate.

## Out of scope

- Query expansion (planned but dropped from M5).
- A new cross-encoder model.
- BM25 tuning.
- Surfacing the re-rank score in the UI (that is M7).
```
